Super-Agent 架构设计：让 Agent 跨会话干活，人只面对一个入口#

linux.do 上有个帖子叫《通了个宵，终于把 Super-Agent 架构玩明白了。》，作者 cxuanAI，解读的是 DeepSeek Harness 团队的《Super-agent 设计探索：迈向更自主的 Agent 系统》。帖子把架构拆成五块：双层架构、事件驱动、多信道交互、计算状态与环境的分离，以及 Watchdog。原文开头自己说明了，这是一篇面向工程实践的架构思路探讨，不是对 DeepSeek Harness 现有产品功能的介绍。

下面先按这个顺序把架构讲清楚，后半段再说我自己的看法。

什么是 Super-agent#

近一年模型和多 Agent 的能力都在增强，人参与底层执行的比重在下降，位置挪到了顶层决策和验收。年初 OpenClaw 这类工具就演变成了 Personal Agent。

DSH（帖子对 DeepSeek Harness 团队的简称）的判断是，现有主流 Agent 都在单个 Session 里工作，Session 之间相互独立。手动切 Session，人的注意力跟不上，人大概只能同时盯 3–5 个 Session。单任务的上限取决于模型能力，多任务的上限取决于人的注意力。MCP 解决了扩展性，上下文混乱、单会话同步阻塞这些问题还在。

他们提出的 Super-agent 架构要打破单任务之间的上下文隔离，让 Agent 跨会话保持上下文、同时推进多项任务，用户始终只面对一个 Super-agent。帖子用四个词概括它：连续、高效、主动、持久。

和 Claude 那篇文章的区别，cxuanAI 自己也说了。Claude Code 走的是「单 Agent + Main Loop」，把适合合并的 subagent 流程提炼成 Skills，读写交给 Tools/MCP。那篇讨论的是一项任务内部多个专家 Agent 反复交接会不会丢信息、增加延迟；DSH 这篇讨论的是一组任务怎么长期并行推进，同时让人少操心。

帖子里给的场景是开发者在 IM 终端和 GitHub 之间连续推进，Agent 观察群组反馈，遇到相关问题先评估、定位原因，然后主动修复。

作者还提到 yetone（Magpie 作者）的工作流，三个 /loop 循环，分别盯 GitHub、盯 X 上的反馈、盯代码。DSH 认为单个 ReAct Loop 撑不起上面那四个特点，得从计算机底层切入，Session 共享、缓存、fork、Worktree 和文件系统都是要动的地方。

双层架构：Router 与 Worker#

这里要解决的权衡很直接。所有工作交给一个 Session，连续性强，吞吐低；交给很多 Session，吞吐高，但 Session 割裂，任务过于独立。

Router 是常驻的全局路由层，负责与人交互和协调，所有跨任务的信息和决策在这一层汇总，它不执行具体任务，相当于秘书和大总管。这一层在结构上可以是多节点的，实现上不必局限于单个 Session，DSH 自己用的是单个常驻 LLM Session，原文说实测并没有成为吞吐瓶颈。它和 Agent Teams 的 Team Lead 不同，Router 只管分发、不管任务细节，往往用轻量级模型就能兼顾速度和效果。

Worker 执行具体任务，各 Worker 上下文隔离，挂载完整执行工具，在独立上下文里专注单一任务，需要能力最强的模型。多任务时各自推进，Worker 之间不需要相互通信。Worker 也是多节点，执行复杂任务时可以 fork subagent，本身就能成为一个 Agent Teams。

效果是上下文管理和并发被系统在底层接管，用户侧淡化了 Session。cxuanAI 的看法是，很多 multi-agent 项目把用户当成项目经理，这条路线不对，「Session 不能成为用户负担」。

事件驱动：Trigger、降噪与路由#

Trigger 是群聊消息、邮件和日程提醒、代码审查评论、CI 运行结果这类环境事件。有了 Trigger，Super-agent 能主动发现并执行任务，不必等用户输入 prompt（拉取式）。一条事件要走完过滤、路由、上下文组织，再提前行动。

降噪分两层。第一层是程序层策略（Fast Path），用规则过滤噪音，大部分消息在这一层就没了。第二层是语义层策略（Slow Path），剩下的消息交给 LLM，按提示词写的策略和上下文判断是否需要行动。

为了减轻 Router 的负载，过滤后的消息直接路由给 Worker，全局 Router 只负责新任务的冷启动与跨任务协调。

Thread：订阅与直通#

Thread 是一串相关 Trigger 连成的线，具备连续、完整的上下文，比如一个 GitHub Pull Request、同一封邮件的往来，或同一 IM 话题下的消息。一条 Trigger 是一个点，一串连成一条线。一个 Worker 可以同时订阅好几条 Thread。

后续消息发给谁有两条路。新出现的 Thread 还没人认领，走 Slow Path，由 Router 判断归谁管，建一个 Worker 并让它订阅。Thread 已经有人订阅，就走 Fast Path，后续消息由程序直接投给订阅它的 Worker。

上下文：Inline / Spill 与链式召回#

上下文注入过多会挤占窗口、稀释注意力；过少会让模型反复调工具读取，轮次跟着增加。

Inline 把近期很可能用到的信息直接内联进当前上下文，省掉工具调用的往返。Spill 则把超出窗口预算或低频使用的完整信息留在窗口外，窗口内只留引用或摘要，供模型按需读取。

cxuanAI 打了个比方，这套做法类似操作系统内存页的换入换出。区别在于缺页由硬件和内核自动处理，LLM 没有这个机制，被 Spill 出去的内容要模型自己意识到并主动读回。所以它对模型的要求更高，同一套机制换个模型，效果可能差很多。

链式召回（Chain of Recall）给 Trigger、Thread、Worker 都编 ID，注入时顺手带上下一跳的 ID，对象之间在底层连成引用图。群里问「昨天那个问题修得怎么样了」，Router 顺着消息上的 Thread ID 找到处理它的 Worker，Worker 状态里挂着 PR 的 Thread ID，再查到修改记录。这里靠的是一张能实时渲染的地图，不需要一个巨大的记忆库。

投机执行：提前行动#

这一块借鉴计算机系统的投机执行（Speculative Execution）。结果还不确定会不会被采用时，先按环境信号在后台尝试，用额外的后台算力换人的等待和介入成本。结果有价值就交付，没价值就丢弃。

多信道交互：异步 ReAct Loop#

传统 ReAct 是一问一答的阻塞式，run() 发出后整个循环卡住等结果，新消息只能排队。异步 ReAct Loop 类似全双工，start() 立即返回「已启动」，循环继续跑，工具执行完再把结果送回，会话不必等上一个任务完成就能接新指令。

帖中说这套异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。

cxuanAI 补充说，Claude Code 的后台 subagent 可以和主对话并行、跑完通知，ChatGPT 长任务运行时也能继续补充要求，两家都有类似能力。

计算、状态与环境的分离（BYOM）#

计算是正在跑的 Agent Loop，状态是会话记录和任务记录，环境是代码仓库、本地文件、工具链。三样都在一台电脑上时，电脑一关 Agent 就干不了活，换台电脑环境也没了。

帖中称之为存算分离（Compute-Storage Separation），分两步走。

第一步把计算和状态分开。Agent Loop 放进云端可替换的容器，会话状态单独存数据库。容器挂了换一个，状态还在就能继续。

第二步把计算和环境分开。本地环境不搬上云，真实环境里有未提交改动、私有凭据、特定硬件和工具链，搬上去结果大概率不同。反过来在端上装一个轻量 daemon，只负责执行命令、回传结果。

这样做的结果就是 BYOM（Bring Your Own Machine）。个人电脑，甚至时不时才上线的机器，都能接入。前提是云端和端侧互相信任，云端一旦被攻破，连着的所有设备都危险。

Watchdog（看门狗）#

持久在线的分布式系统很难只靠主系统内部逻辑保证长期可靠，需要在主系统之外引入独立的外部控制回路（Control Loop）。

进程存活探测和心跳脚本不够用。很多时候进程还在，问题出在 LLM 内部循环死锁，或者偏离了执行目标。

DSH 配置了一个 Watchdog Session，由定时消息驱动，负责及时介入、发现异常、纠偏和故障恢复。它本身也是一个 Agent Session，开发者可以直接问它错误原因，及时调整。

我的看法#

讲完架构，说几句我自己的判断。这几点基本上和 cxuanAI 在帖子里的态度一致，我用原文的材料再走一遍。

我盯这套东西是有私心的，因为手上正在做序场。序场是我用 Grok Bot 搭的一套多 bot 研发流程，要解决的就是一件事：人的精力有限，一口气开七八个会话，看不过来也记不住。在序场里我给自己定的位置只有三样，定目标、拍板、授权。

另外一半想法来自 yetone。Magpie 那套工作流是事件驱动，三个 /loop 分别盯 GitHub、盯 X 上的反馈、盯代码，有事才动，人不用守着。我照这个思路在改序场，事件触发那块还没接上。所以 DSH 这篇出来时，我的感觉是它把我零碎在做的事系统化了一遍，规模也大得多。

用户不该给 Session 当项目经理#

帖子最扎我的是「Session 不能成为用户负担」这句。现在的多 Agent 工具，用户在干的活其实是排班和传话：这件事交给谁、上下文喂到哪一步，结果又怎么带回来。cxuanAI 说很多 multi-agent 项目把用户当成项目经理，这条路线不对，我认同。

按双层架构的分法，这些活本来就该由系统接管，用户只需要说清目标、验收结果。Router 这一层存在的意义也在这里，它替人守着全局，人不用自己去记「某个上下文里到底有没有某条信息」。

动的是底层#

cxuanAI 认为很多大模型在玩概念炒作，DSH 的做法是从底层动刀子，没去堆 tools 和 skills。他还说 Agent 架构绕来绕去绕不开计算机底层那些东西，与其搞一堆华而不实的东西博眼球，不如优化底层，他把这条看成 DeepSeek 走向 AGI 的路子。这些我都赞成。

文章里每个模块几乎都能对上计算机系统里的老问题：Fast Path 与 Slow Path 的分流、把上下文窗口当 Cache 来管、跳着取数据的局部性、投机执行，还有存算分离和主系统之外那层 Control Loop。原文结语自己也承认，他们没有提出全新的理论，只是把经典工程思想搬到 Agent 系统上。难的地方在于肯把 Agent 当系统来设计，靠调提示词堆工具出不来这套东西。

代价压在模型身上#

上下文那一段里有句话很关键：操作系统的缺页由硬件和内核自动处理，LLM 没有这个机制，被 Spill 出去的内容要模型自己意识到并主动读回。所以同一套机制换个模型，效果可能差很多。

这一点我完全同意，也解释了为什么这套设计很难做成一个跟模型无关的通用中间件。架构能规定信息怎么分层、什么时候内联、什么时候外溢，最后那一下「想起来去读回」还是得模型自己完成。模型差一档，同一张架构图跑出来的东西就不是一个东西。

安全是这条路线的硬门槛#

计算和环境分离换来了持久在线，代价是把用户的本地凭据和私有代码挂在一个常驻云端的 Agent Loop 后面。原文把「云端一旦被攻破，连着的所有设备都危险」写在前提里，其实这是整条路线的门槛，不是脚注。

这一条不解决，BYOM 就只能在一个很小、很可信的范围内用。想大规模接入个人电脑和公司内网机器，得先回答云端被攻破之后端侧怎么活。

最值得先抄的两件事#

如果只挑两件马上能做的事，我选拆分和看门狗。把「谁负责分派」和「谁负责干活」拆成两层，以及给系统配一个在外部定时巡检的 Watchdog，这两件都不需要换模型，改的是系统结构。帖子里的其余部分，比如链式召回、投机执行，都要等前面这两件站稳了才有意义。

这条闭环的终点#

五个模块拼起来看，指向的是一条自动化闭环：事件自己进来，任务自己分派，上下文自己组织，异常自己恢复，人只在需要决策和验收的地方出现。这正是我想在序场里验证的东西，区别在于 DSH 把它做成了系统，我是在一套 bot 流程上试。

所以我读这篇文章，最关心它怎么回答「人还剩下什么」。cxuanAI 说这是 DeepSeek 实现 AGI 的路子，我认同这个方向，把人的位置往上抬一层，让机器接管底下那些串行、等待、传话的活。能走多远，卡在我上面提的那两处：云端被攻破之后端侧怎么活，以及模型能不能自己知道缺了什么。
