WeKnora 学习笔记：从父子分块到 Rerank，再到模型实际读到的证据#

学习 WeKnora 时，我从父子分块开始，沿着几个问题往下追：父子关系由谁决定？父块不做向量化，怎么找到它？多个子块命中同一个父块，会不会重复发给模型？重排留下一个子块，模型最后就只读这一块吗？

这些问题要放到同一条处理链路里看。切块决定内容如何组织，召回和重排选择候选，父块扩展补充背景，发送前还要把内容整理成可以准确引用的来源。只看到其中一个阶段，很容易误判最终模型输入。

本文整理自 2026-10-17 的学习记录，依据 WeKnora 提交 d3d4963。主要讨论普通文本 RAG 聊天路径；其他搜索入口以及 FAQ、图片和图谱有各自规则。

需要先说明验证范围。学习过程中实际运行了文本切块代码，得到 2 个父块和 20 个子块；存储与重排及引用流程来自当时的源码及现有测试阅读，没有执行这份文档的向量化和建库，也没有进行检索或模型调用。下文的查询和评分示例均为假设，本次博客整理也没有重新运行 WeKnora。

先把小块检索和大块上下文分开#

只用大块检索，一个块可能混入多个话题，具体证据容易被其他内容稀释。只用小块，虽然能定位到某句话，却可能丢掉它的前提、适用条件和例外。

父子分块提供两种粒度：子块承担较细的检索，命中后沿父级关联读取更大的内容范围。这适合技术排障、产品手册，以及需要结合上下文理解的制度条款。材料本身很短，或小块已经能完整表达所需信息时，多一层父级可能没有收益。

WeKnora 的父子关系在切分时就确定了。处理顺序可以写成：

向量模型负责后面的文本表示与相关性检索。父子块边界由切分策略、文档结构和长度配置确定；命中子块后读取父块，也直接使用已保存的 ID。

在 auto 策略下，程序会根据标题等文本特征选择策略，验证结果，必要时继续尝试后续策略。每个父块内部会重新选择，所以父层与子层不一定采用同一策略。空策略则为兼容旧配置走 legacy，不能把所有知识库都理解成自动按标题切分。

父子两层复用了同一套切分接口，配置由 DeriveParentChildConfigs 统一推导。预览与实际入库共用这部分逻辑，可以减少两边配置推导不一致的问题。

C16 的标题上下文单独保存在 ContextHeader，正文保存在 Content。其中关于恢复机制的原文是：

AUTO_RECOVER_DIRTY 默认开启，启动时会尝试重设迁移版本并重跑。这是重试机制，不能修复扩展缺失、磁盘不足或手工修改导致的 schema 差异。

这一节还明确说明，force 只修改迁移版本标记，不执行回滚 SQL。这个具体区别，后面可以用来理解重排要解决的问题。

这次切块运行使用了 11 份与仓库文件字节一致的切块源码，在隔离环境中省略日志输出，并抽取原样图片辅助函数，绕过 Windows 下无关的 SQL 解析依赖。它验证的是切块结果，不能据此推断检索效果。P2、C16 也只是演示别名，实际入库会生成 ID。部分表格子块会补表头，因此块正文也不一定是原文中的一个连续切片。

父子块存在哪里，哪些参与向量化#

在普通文档的父子文本入库路径中，父子块正文都保存在业务关系库的 chunks 表。

记录类型业务关系库这条文本流程的检索索引
父块 P2parent_text保存正文、归属及位置等字段不为它创建索引记录，也不生成其向量
子块 C16text保存正文、标题路径及 parent_chunk_id 等字段创建索引；启用向量检索时计算向量

父子块使用同一个数据模型和同一张表。子块的 parent_chunk_id 指向父块的 id。处理时先批量保存父子记录，再筛出 text 类型为后续索引准备输入。

这里有两个限定。第一，只有启用向量检索才会计算向量。第二，“父块不向量化”针对这条普通文本入库路径，不能扩大成整个项目只有子块这一种可索引内容。

子块送给 Embedding 模型的文本也不一定只有 Content。这条流程先通过 EmbeddingContent() 补入已有标题路径，再添加非空文档标题。

这些信息补足了短文本的标题语境，没有把整个父块塞进每个子块的向量化输入。数据库里的正文与标题路径仍是独立字段。

父子分块与“双库回查”怎么区分#

如果向量索引命中 C16，再按 id = C16 到业务库读取正文，取回的仍是同一个小块。继续沿 parent_chunk_id 读取 P2，才扩大了上下文范围。

普通索引回查处理索引与业务记录的对应关系；父子分块处理内容粒度和上下文扩展。二者可以组合，也不必对应两个物理数据库。例如 PostgreSQL/pgvector 驱动的检索记录使用 embeddings 表，其中也能保存 content。

“向量加关键词双路检索”则属于混合召回，处理的是如何补充候选。它可以发生在父块扩展之前，同样不由物理数据库个数定义。

Rerank 发生在父块扩展之前#

在这条聊天路径中，系统先按召回 ID 批量读取子块正文与父级关联，处理候选并重排，然后在 Merge 阶段读取父块。聊天检索显式跳过提前上下文增强；其他搜索入口可能提前增强，不能直接套用同一顺序。

向量召回和 Rerank 都在判断相关性，但计算方式不同。

环节常见做法作用范围
单向量召回文本向量预先计算，查询编码后比较相似度从较大的知识库找候选
Rerank将当前问题与候选文本交给相关性评分模型对已经得到的候选重新评分

典型交叉编码器会把问题和文本放进同一次网络计算，让词语相互作用，通常比比较预计算向量更昂贵，适合较小候选集。WeKnora 通过统一接口接入配置的服务，没有把所有 Rerank 模型固定为一种 Cross-Encoder 架构。

它也没有在重排阶段再算一遍余弦相似度，或要求生成回答的聊天模型逐条写评语。应用侧接口接收 query 和 documents，返回候选下标及相关性分数，映射回原来的块。

模型打分前，候选文本还会加工#

聊天插件使用 RewriteQuery，传入的候选可以来自向量或关键词等路径，所以后续的 base_score 应理解为原召回分数。

插件设置 MaxCandidates = max(200, RerankTopK)，共享逻辑按原分数预选并排除空文本。图谱有另外的保留规则，因此 200 不能理解成所有类型的绝对上限。

普通文本的 ModelPassage 包含可用的文档标题、标题路径与清洗后正文，还会读取已有图片描述、OCR 文字和生成问题等补充内容。这一阶段不会凭空生成缺失信息。清洗会移除部分 Markdown、URL 及表格分隔格式，保留代码和公式内容，并按所配模型的段落长度限制适配。

协议适配层还会处理分批请求与下标恢复，对声明为 logit 的分数使用 sigmoid 转换尺度。这个转换不保证不同模型的分数已经校准成相同含义。

模型分、综合分与 MMR 要分开看#

WeKnora 先用模型相关性分数与 RerankThreshold 比较。没有候选通过，且原阈值大于 0.3 时，会尝试一次 max(原阈值 × 0.7, 0.3)；仍未通过时，普通策略允许达到保底分的模型 Top-1 留下，默认保底分为 0.15。聊天检索目标带显式召回阈值覆盖时，保底参数另设为负无穷。因此配置阈值也有放宽与保底规则。

通过筛选后，普通非 FAQ、非图谱结果使用下面的综合分：

通常来源权重为 1，web_search 为 0.95。图谱使用模型分替代同类召回分，FAQ 优先设置也可能带来额外加权。原召回分、模型分与综合分分别保存在 base_score、model_score、composite_score，便于解释排名变化。

之后还有 MMR，默认 lambda = 0.7，选择时兼顾综合相关分与已选内容的重复程度。

这份实现用文本 token 集合的 Jaccard 重叠估计重复度，不再调用向量模型。用于重复度比较的文本特意不加共同文档标题，避免同一文档的不同子块仅因标题相同就被过度视为重复。

所以最终保留集合不一定等于模型分最高的 K 项，也不一定等于综合分最高的 K 项。MMR 只能减少候选冗余，不能保证逐字去重。

假设问题是“Dirty 状态下，force 命令会执行回滚 SQL 吗？”，来源权重为 1，重排阈值为 0.2，三个候选都送到模型。

以下分数全部是讲解假设，没有实际执行查询或调用重排模型。

候选内容范围假设向量召回分假设模型重排分按公式计算的结果
C19磁盘不足与 Schema 差异0.880.22综合分 0.496

这个例子展示了一种可能的排名变化。同属迁移主题的内容先被召回，直接回答 force 行为的 C16 在重排后优先。它不代表 C19 实测向量分一定更高，也不保证重排每次判断正确。

Rerank 无法找回没进入候选集的证据。没配置模型、模型不可用或调用失败时，聊天流程回到召回结果路径，Merge 再收窄候选；模型成功评分但所有项都不满足有效阈值和保底条件，则可能没有有效检索结果。相关性分也不能当成事实正确概率。

命中同一个父块，会重复发送吗#

假设 C15、C16 和 C17 都命中，且都属于 P2。这个查询没有实际运行，下面按源码流程解释。

读取父块时，先按父 ID 去重#

resolveParentChunks 把父 ID 收集进集合，再批量读取。本次待查集合只有 {P2}，不会为三个命中分别查询一次父块。

这只说明该次扩展读取的去重行为，既不是跨请求缓存，也不代表引用构建等后续阶段不会再读取相关记录。各搜索结果此时仍保留自己的子块 ID。

扩展与合并时，比较当前正文#

JoinChunkContent 合并父正文和子正文。正常纯文本场景中，父正文已经包含子正文，结果就是父正文，因此多个子块扩展后可能得到相同内容。

后续按 KnowledgeID + ChunkType 分组，按 ChunkIndex 排序，再合并可合并结果。扩展后会标记 ContentRewritten = true，使用当前文本包含关系或索引相邻关系判断，不再盲信旧字符坐标。

相同正文或安全的全文包含只留一份，否则尝试首尾重叠拼接，必要时保留两段。分组合并会记录被合并子块 ID 和来源定位，保留较高分；但不能承诺所有后续去重分支都完整保留命中谱系。

项目初始去重不会简单地“同父只留一个子块”，因为不同子块可能各自包含有效内容。

内容去重与来源去重各有一层#

Merge 还会按结果 ID、规范化全文签名，以及内容包含和近似重叠过滤重复项。全文签名是转小写、整理空白后计算 MD5。近似重叠分支在两侧 token 集合大小比不超过 3 倍时，检查较小集合的 token 重叠率是否达到 0.85，优先保留高分项，同分保留更长正文。

这里的 0.85 是词元集合重叠系数，既不是字符相同率，也不是 embedding 余弦相似度。

发送模型前还要整理引用来源。attachCitationSources 会读取命中或合并来源，并查找相关父块下的兄弟块，检查启用状态、文档与知识库归属，以及正文有效性和覆盖关系，排除 parent_text 作为这个阶段的独立来源。

expandCitationSources 随后按来源自己的 ID 全局去重，prepareMessagesWithModelContext 使用各来源的正文构造实际模型输入，替换中间渲染内容。核实失败的改写上下文不会直接冒充原始证据。

这里因此至少有三种不同的去重对象：父 ID 用于减少读取，当前正文用于合并冗余上下文，来源 ID 用于避免同一证据重复输入。来源 ID 唯一，仍不能保证不同子块之间没有切分 overlap。

最后按子块提供证据，父块扩展还有什么用#

父块扩大了可用内容范围，来源子块保留各自的证据身份。最终来源可以包含最初没有命中的兄弟块。

沿用真实切块结构，假设最初只命中 C16。

如果 P2 的扩展结果被保留，C12～C20 全部启用、正文有效且满足覆盖检查，模型可以收到这 9 个子块。它们不需要逐个再次通过向量召回，也不代表整篇文档都被加入。

原有测试 TestExpandedContextHasSeparateCitationBodies 也体现了这一点：未作为独立搜索结果输入的兄弟记录，整理后仍能以自己的正文出现；禁用块和其他文档的块被排除。学习时只阅读了该测试，没有运行它。

这样可以让父级背景中的其他段落以实际子块身份被引用，避免把补入内容都归到最初命中的 C16 名下。

Top-K 限制不了最终输入 token 数#

在本轮检查的普通文本路径中，新增兄弟块没有再次逐个按问题相关性重排。来源资格和正文覆盖检查，只能确认它属于当前扩展内容，不能证明它适合回答当前问题。

例如问题只涉及 Dirty 状态，C19 的磁盘不足说明仍可能随 P2 进入输入。重排即使选中了 C16，后续扩展也可能重新带入其他主题。

流式 RAG 的相关阶段可以概括为：

显式的合并后 FILTER_TOP_K 位于 rag_stream；非流式 rag 配置没有这个阶段。图谱等特殊结果另有保留规则，也不能把 K 当作所有类型都绝不越过的上限。

即使合并后 Top-K 为 1，保留下来的那一条 P2 上下文仍可能展开成 9 个来源。这三个量需要区分。

  • 合并结果数，表示中间留下几条上下文。
  • 最终来源块数，表示实际展开出几份原始证据。
  • 输入 token 数，还包括提示词、历史、记忆与当前输入等内容。
控制项能控制什么边界
父块大小与切分策略一次扩展的内容范围过小可能丢背景，过大可能混入其他话题
召回数量与阈值初始候选规模多查询、多目标及特殊结果影响总量
RerankTopK 与阈值扩展前候选，流式链路还用于合并后筛选没有按最终来源数或输入 token 数计算
合并与去重减少重复内容和来源不能过滤全部无关内容或消除全部 overlap
历史 MaxRounds加载的历史轮数每轮长度不同
MaxTokens / MaxCompletionTokens模型生成输出预算不能限制输入证据长度

源码里还有 350/850 rune 的短上下文邻居扩展阈值。这是局部补充规则，不会把所有父级扩展统一裁到 850 字符；来源整理时还可能使用邻居的完整原始正文。重排模型的单段输入限制，也只约束重排请求。

在已检查的普通 RAG 路径中，未见对最终完整消息统一计算输入 token、再按生成模型窗口分配预算的裁剪步骤。这个结论仅限该提交和本轮检查路径，不能推成整个项目没有长度管理。

Agent 执行引擎另有 manageContextWindow，包含 token 估算、接近阈值时压缩，以及压缩后仍超预算时裁剪工具结果的机制。普通 RAG 不能直接套用这套行为。

这条链路的取舍#

WeKnora 把检索粒度、扩展范围与引用身份分开处理：子块便于定位，父块补充背景，实际来源负责准确引用。实现上也分别使用父 ID 集合、正文合并与来源 ID 去重，避免用一个简单的去重键承担所有职责。

代价同样具体。父子正文重复存储；父块越大，补入低相关内容和增加输入长度的可能性越高；扩展前的重排无法逐个筛掉之后才加入的兄弟块。

材料里的父块如果经常混入多个独立话题，可以先检查父块边界与大小，再结合候选数量和重排配置验证。父块也不能一味缩小，否则前提与例外可能再次被切散。

进一步的设计可以考虑扩展后对新增来源评分，在来源展开后计算完整消息的 token 预算，并记录最终来源数和输入 token 数。这些是学习记录里的改进方向，不属于本轮确认的已实现行为。

对我来说，这轮学习留下的检查方法是从一次命中继续追到模型消息，不停留在搜索结果或 Merge 输出。想知道模型到底读了什么，要看最终来源展开；想知道输入是否可控，还得看完整消息的长度，而不能只看 Top-K。
